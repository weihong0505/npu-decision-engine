## 一、结论矩阵

### 结论线 1 · LLM 解码：NPU 不如 CPU

| 指标 | NPU | CPU | iGPU | dGPU | 权威文件 |
|---|---|---|---|---|---|
| 短问答 p50（max_new=24） | 3304.8 ms | **553.2 ms** | 1189.8 ms | — | `decision-latency.json` |
| 吞吐（max_new=24） | 3.6 tok/s | **19.7 tok/s** | 18.6 tok/s | 7.9 tok/s | `decision-latency.json` |
| 吞吐（max_new=128） | 6.55 tok/s | **28.14 tok/s** | 25.9 tok/s | 7.79 tok/s | `results-1.5b.json` |
| 吞吐（长 prompt/512 new） | 10.6 tok/s | **28.71 tok/s** | 25.1 tok/s | 6.71 tok/s | `results-1.5b-long.json` |

**结论**：自回归解码在 NPU 上稳定慢于 CPU。CLI 之外的补充读数见
`rerun/`：本次重跑 NPU 变快（3.6→5.6、6.55→7.73、10.6→10.64 tok/s），
CPU/NPU 比值从 5.47× 收到 3.88×，**long 模式的比值几乎不变（2.71× → 2.76×）**，
所以"NPU 慢"定性成立，但"慢 5 倍"这个具体倍数随驱动/协议变化，别当常数用
（详见下文"协议陷阱"）。

### 结论线 2 · ModernBERT 编码器：静态形状是前提

| 形状 | NPU | CPU | iGPU | 权威文件 |
|---|---|---|---|---|
| 动态 `[?,?]` | **编译失败** | 37.24 ms | 34.05 ms | `modernbert-npu.json` |
| 静态 L=128 | **38.39 ms** | 60.68 ms | 47.33 ms | `modernbert-npu-static.json` |
| 静态 L=128（repeat=30，含 TURBO） | **37.46 ms** | 65.69 ms | 46.51 ms | `modernbert-tuned.json` |
| 静态 L=768 | **253.27 ms** | 383.03 ms | 282.67 ms | `scaling.json` |

长度扫描 `scaling.json`：`npu_over_cpu` = 0.65 / 0.61 / 0.55 / 0.61 / 0.66（L=128→768），
**NPU 全程快于 CPU，比值稳定在 0.55–0.66**。

### 结论线 3 · JEV-lite：整图不行，拆图可行

| 方案 | 结果 | 权威文件 |
|---|---|---|
| 整图 → NPU | **编译失败**（22 个 `IsNaN`） | `jev-npu-final.json`、`jev-error.txt` |
| 整图 → CPU | 568.43 ms（可跑，作为对照） | `jev-npu-final.json` |
| 补掉 `IsNaN` 后整图 → NPU | 1624.78 ms，且 `max_abs_err=0.812`（精度崩） | `jev-fixed.json` |
| 拆图：NPU 编码器 + CPU head | **189.01 + 0.199 = 189.18 ms** | **`jev-hybrid-final.json`** |
| 拆图前的那次尝试 | NPU 1616 ms > CPU 552 ms（形态没修，无收益） | `jev-hybrid.json`（已被取代） |

对照：整图 CPU 568.4 ms → 拆图后 **3.0×**。

### 结论线 4 · 模型质量（与 NPU 无关，但决定这东西有没有用）

| 配置 | accuracy | ECE | 权威文件 |
|---|---|---|---|
| 微调模型单独 | 0.6490 | 0.0769 | `eval.txt` |
| 冻结探针单独 | 0.6695 | 0.0384 | `ens.txt` |
| **集成（w=0.50 + 锐化 T=0.50）** | **0.7005** | **0.0288** | `ens.txt` |
| TypeSafe Jev 1.13.0（引用值） | 0.7270 | 0.1440 | `ens.txt` |
| 多数类基线 | 0.4830 | — | upstream README |

**校准是免费的**：`calib.txt` 显示按共识分布训练后温度拟合返回 T=1.000，
强行施加反而让 ECE 变差（0.1082 → 0.1424），脚本因此保留 T=1。
**置信度可路由**：阈值 0.90 时 18.5% 流量拿到 95.4% 准确率（`ens.txt`）。

## 三、冲突裁决：TURBO 到底有没有用？

| 文件 | 测法 | 结论 |
|---|---|---|
| `modernbert-tuned.json` | 各配置**各跑一次**（非配对） | `NPU_TURBO=YES` 比默认快 **+14.7%** |
| `modernbert-ab.json` | **配对**：两配置各编译一次，4 轮交替顺序，取轮内 p50 | 真实增益 **−0.72%**，轮间波动 0.16–2.31% |

**裁决：采信 `modernbert-ab.json` —— TURBO 无可靠收益。**

理由：配对设计消除编译状态与顺序效应，且给出了轮间波动；而单次扫描的 +14.7%
落在波动量级之外却被后续配对测量证伪，属典型的单次测量伪影。
`modernbert-tuned.json` **保留但标注为"非配对测量，不作结论依据"**——
这正是本项目"优化好到可疑必然有诈"的实例。

## 五、协议陷阱（读旧数字前必看）

1. **`decision-latency.json` 的 NPU 延迟含"提前 EOS"偏差**：旧测量 5 轮均值只生成 12 token
   （撞 EOS 提前结束），而脚本设定是 24。重跑跑满 24 token 后单次耗时反而从 3304.8 → 4207.3 ms。
   所以该文件的 `tok_s` **不能**直接与跑满 token 的配置比。
2. **设备能力对比只看 `results-1.5b-long.json`**：那里 token 数充足，
   新旧 CPU/NPU 比值 2.71× → 2.76×，是唯一干净的对照。
3. **`max_abs_err` 不是精度指标，只是"同一图在设备间的差异"**：见
   [docs/03-约束与踩坑.md](03-约束与踩坑.md#4-数值一致性比想象中脆弱) ——
   本次整理发现，同一份权重换一条导出路径，隐藏状态就能差 23，
   远大于那个 0.024。

## 六、权重归属：一个必须交代清楚的问题

原结论里"NPU 编码器 189 ms"跑的是 **02:46 导出的权重**，而 `jevlite.pt` 在当天
**12:38 被 `03_calibrate.py` 重新落盘**。本次整理为此写了
`src/bench/bench_jev.py --mode verify` 与 `src/tools/onnx_weight_fingerprint.py` 去核对，
结果是**两者不同源**（46/46、47/47 个可配对张量均不一致）。

- **不受影响**：所有**延迟**结论（延迟与权重取值无关）。
- **受影响**：任何"ONNX 产物 = 当前检查点"的表述，以及把 `max_abs_err` 当权重保真度读。
- 详见 [docs/03-约束与踩坑.md](03-约束与踩坑.md#5-onnx-产物与当前检查点不同源已证实)。
