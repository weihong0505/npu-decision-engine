# 03 · 约束与踩坑

按"踩了会浪费多少时间"排序。前三条是本项目所有 NPU 结论的总开关。

> **如果你现在就要在 NPU 上跑 JEV**：先看 [第 9 节](#9-npu-编译-jev-图会直接段错误2026-10-环境回归)。
> 2026-10-15 复测时，NPU 编译 JEV 那两个图会**让进程直接段错误**，不是异常、抓不到。

---

## 1. NPU 只接受静态形状（最重要的约束）

```
动态 [?,?] → NPU 编译直接失败（ze_graph_ext_wrap 异常）
静态 [1,N] → 编译通过，且比 CPU 快
```

失败形态：`modernbert-npu.json`（动态，NPU 报错）、`jev-npu-final.json`（整图含动态维，NPU 编译失败）。
成功形态：`modernbert-npu-static.json`、`scaling.json`。

做法：导出/读入后显式 `model.reshape({...: [1, seq]})`。
**代价**：序列长度从此写死，换长度要重新编译（NPU 编译 2–37 秒，见下）。

> 背景：据 Intel 材料，NPU 的动态形状支持是 Lunar Lake 一代才有的能力；
> 同代（Intel Core Ultra 200 系）平台的 NPU 同样受限。

**编译开销不是免费的**：NPU 首次编译 2.19 s（TURBO 时 35.59 s）vs CPU 1.58 s。
所以"NPU 更快"只在**编译一次、推理多次**的场景成立。用 `CACHE_DIR` 缓存编译产物
可以把首次成本摊掉，但实测缓存没带来额外收益（`modernbert-tuned.json`：TURBO+CACHE 比 TURBO 还慢 0.4%）。

## 2. NPU 不支持 `IsNaN`

`jev-error.txt` 的根因就在这里：

```
Unsupported operation node_IsNaN_247 with type IsNaN and version opset10
图里共有 22 个 IsNaN（总算子 1960）
```

`IsNaN` 来自 PyTorch 导出时的 masked-softmax 惯用写法。
把它替换掉之后 NPU **能**编译，但：

| 方案 | 延迟 | `max_abs_err` |
|---|---|---|
| 整图 → CPU | 568 ms | — |
| 补 `IsNaN` 后整图 → NPU | 1625 ms | **0.812** |

慢了 2.9 倍且精度崩掉（0.812 量级意味着 argmax 都可能翻转），**这条路是死的**。
正解是第 3 条：拆图。

## 3. 拆图是唯一可行的路

依据 `engine/model.py:54-59`，整个模型只有两部分：

```
encoder（150M，224 MB 权重）  →  last_hidden_state
head   = gather(label_pos) → Linear(768,1)  →  [B, M]
```

head 只有 `score.weight[1,768]` + `score.bias[1]`，在 CPU 上只要 **0.2 ms**。
于是：**编码器给 NPU，head 留 CPU** → 189 ms，是纯 CPU 整图（568 ms）的 3.0 倍加速。

这也是 `--mode hybrid` 能复现的原因：head 用 numpy 逐位重写（`tests/test_head_parity.py`
保证它与 torch 实现等价），所以不依赖 torch 前向就能量出真实端到端延迟。

## 4. 数值一致性比想象中脆弱

整理时发现的一个反直觉事实：**同样权重、换一条导出路径，隐藏状态就能差 23。**

```
两个 ONNX 文件的权重指纹完全相同（采样张量 delta 均为 4.134e-03 / 7.831e-04）
但它们的输出互相之间 max_abs_err = 22.97
各自与 torch 参考的输出差 = 28.5 / 28.8
三者范数相同（|h| ≈ 969 / 994 / 1000），相关系数 0.93
```

**同权重、不同输出、差 23** ⇒ 差异来自计算语义（ModernBERT 的滑窗局部注意力 /
RoPE 位置处理在不同导出与实现路径下的差异），而不是权重。
想用"把序列缩到 128 再比一次"来验证这条的路也走不通 ——
两个编码器 ONNX 都把 768 烘死在常量里，reshape 到 128 会被形状推断直接拒绝
（见 `rerun/verify-encoder-weights.json` 的 `short_seq_check`）。

**实践含义**：`jev-hybrid-final.json` 里的 `max_abs_err`（NPU 0.024、iGPU 0.078、CPU 3e-6）
**只能读作"同一次运行内、同一张图在不同设备上的差异"**，不能读作"模型精度"，
更不能用它证明"NPU 精度够用"——上层实现路径的分歧比这个大得多。

## 5. ONNX 产物与当前检查点不同源（已证实）

`output/results/export-out.txt` 记录了导出当时的自检：
`parity vs pytorch: max abs diff 6.32e-06 OK` —— 说明 **02:46 那份 ONNX 与当时的检查点同源**。
但 `jevlite.pt` 的 mtime 是 **12:38:44**（`03_calibrate.py` 重新落盘）。

本次核对结果：

| 核对方式 | 工具 | 结果 |
|---|---|---|
| 权重指纹（逐张量逐元素） | `src/tools/onnx_weight_fingerprint.py` | `jev_encoder.onnx` 46/46 不一致；`jevlite.onnx` 47/47 不一致 |
| 输出侧对比 | `src/bench/bench_jev.py --mode verify` | 整图 logits 差 1.65；编码器隐藏状态差 28.5 |

`03_calibrate.py:173-176` 只写了 `log_temp` 并附 `temperatures`，理论上不应改变编码器权重
（`ckpt_temperatures` 实测为 `[1.0, 1.0, 1.0]`）。因此**最可能的解释是**：
02:46 之后模型被重新训练/重新保存过一次（训练日志没有留存），
当前 `jevlite.pt` 与所有 ONNX 导出**来自不同的训练产物**。

**待办**（本次未做）：用当前 `jevlite.pt` 重新导出一次 ONNX，然后重跑
`bench_jev --mode verify`，确认指纹一致；此后 NPU 数字与模型数字才归属同一份权重。

## 6. ONNX 侧车权重：改名会炸

`output/onnx/*.onnx` 的权重放在同目录的 `.onnx.data` 侧车里，**侧车文件名被写进了
`.onnx` 文件内部**（TensorProto 的 `external_data.location`）。

整理时把 `enc_dynamo_sdpa_默认.onnx` 改成 ASCII 名，立刻报：

```
Invalid usage of method for externally stored data in file
(enc_dynamo_sdpa_默认.onnx.data, offset: 443547648, ...)
```

修法是重写图里的 `location`：

```python
import onnx
m = onnx.load(p, load_external_data=False)
for init in m.graph.initializer:
    for kv in init.external_data:
        if kv.key == "location":
            kv.value = "enc_dynamo_sdpa.onnx.data"
onnx.save_model(m, p)
```

**推论**：`.onnx` 和 `.onnx.data` 必须同目录、同名配对存放；移动/改名要成对处理并改内部引用。

## 7. 其它一次性踩到的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| **PS 5.1 读 UTF-8 无 BOM 的 `.ps1`** | 按系统代码页(GBK)解码 → 中文注释字节错位 → **解析被破坏**：报 `无法将"Do-Test"项识别为 cmdlet…`、甚至把脚本源码当输出打出来 | `.ps1` 必须存成 **UTF-8 with BOM**；`tests/test_project_hygiene.py` 已加断言守住。修复一行：`[System.IO.File]::WriteAllText($p, [System.IO.File]::ReadAllText($p), [System.Text.UTF8Encoding]::new($true))` |
| 本机没有 `pwsh` | 只有 Windows PowerShell 5.1，`pwsh` 报 CommandNotFound | 用 `powershell -File .\run.ps1`；文档里的 `.\run.ps1` 在两者下都可直接调用 |
| ONNX opset < 18 产出非法图 | torch 仍会 emit 带 `num_outputs` 的 `Split`，ORT 加载时才炸 | 用 opset ≥ 18；导出后必做 parity check |
| INT8 量化在 NPU 上是负优化 | 自导 INT8 → NPU 3374 ms（fp32 是 1613 ms） | 不要为了"省显存"在 NPU 上量化 |
| iGPU 对整图报 GatherND 布局错误 | `No layout format available for gathernd` | iGPU 只跑得动编码器（240 ms） |
| dGPU 经 OpenVINO 极慢 | NPU 37 ms 的任务，RTX 5060 要 1481 ms（慢 97%） | 别把 dGPU 当备选 |
| PowerShell `>` 重定向 | 产出 UTF-16LE + BOM，且把 stderr 混进日志、加一段 PowerShell 报错包装 | `src/tools/normalize_logs.py` 转换并剥壳 |
| 本机 Python stdout 是 GBK | 打印 `✓`/`✗` 直接 `UnicodeEncodeError` 崩掉；中文乱码 | `src/paths.py` 导入时把 stdout/stderr 重设为 UTF-8 |
| 写死盘符路径 | 8 处 `g:\npu-experiment\...`，其中 2 处是 `e:\`（该盘不存在）→ `ModuleNotFoundError` | 统一走 `src/paths.py`；`tests/test_paths.py` 加回归测试 |
| 本机代理被硬编码 | `dl-data.py` 写死 `http://127.0.0.1:<port>` | 改由环境变量 `HF_PROXY` 控制，默认直连 |
| `resize_token_embeddings` 的提示 | 每次加载都打印"new embeddings will be initialized..." | 正常现象（加了 `<<q>>`/`<<l>>` 标记 token），非错误 |

## 8. 数据与形状坑（引擎侧，来自上游 README 与本次核实）

- **label 宽度不固定**：不同 workflow 的标签数不同（16/17/18/20），跨 batch `torch.cat` 会失败，
  所以有 `pad_cat`。ONNX 里 `label_pos` 静态宽度取 **18**。
- **10% 的样本没有 `criteria` 键**（裸 `noul` 问题）：6 行的小样本测试会通过，训练跑到 300 行才炸。
  必须 `smoke_test.py --all` 全量校验（本次整理跑过：8000 个问题 0 处 label/gold 不匹配）。
- **`--max-len` 不能往下调**：state 长度 401–997 token（p50 588），512 会截断 73% 的样本。
- **温度标定要限幅**：无界拟合曾返回 T=400，把分布压平、NLL 好看但置信度信号被毁；
  上游已限幅到 [0.25, 5.0] 并拒绝样本数 < 30 的类型。

## 9. NPU 编译 JEV 图会直接段错误（2026-10 环境回归）

**症状**：脚本**零输出**、没有任何 traceback，退出码 `-1073741819`
（十六进制 `0xC0000005`，Windows 访问违例）。第一次遇到会以为是脚本没跑或输出被吞了。

**定位过程**（逐个隔离，用子进程跑避免连带shell）：

| 测试 | 退出码 |
|---|---|
| `jevlite.onnx` 读图 + reshape + **CPU** 编译 | 0 |
| `jevlite.onnx` + **CPU** 编译 + 推理 | 0 |
| `jevlite.onnx` + **NPU** 编译 | **-1073741819** |
| `jev_encoder.onnx` + **NPU** 编译 + 推理 | **-1073741819** |
| `jev_encoder.onnx` + **CPU** 编译 + 推理 | 0 |

**关键对照**：同一时刻、同一台机器、同样 L=768，
INT4 的 `models/ModernBERT-base/onnx/model_q4.onnx` 在 NPU 上**编译运行正常**（252.82 ms）。
所以不是 NPU 坏了，而是**这个 fp32 JEV 图在当前环境下的编译回归**。

**已排除**：与 `.onnx.data` 侧车无关 —— 把权重合并成自包含单文件后，NPU 编译同样崩溃。
**候选原因**（未隔离）：NPU 驱动/编译器版本变化；fp32 图（570 MB 权重）比 INT4 图（225 MB）
的编译期内存压力大得多，编译器 OOM 时崩在原生层而不是报错。

**为什么 try/except 救不了**：这是进程级崩溃（native access violation），
Python 层根本收不到异常。

**工程对策**：把这类调用放进子进程。`harness.run_isolated_device()` +
`src/bench/_device_probe.py` 就是干这个的 —— 崩了只丢子进程，父进程把它记成：

```json
{"error": "子进程退出码 3221225477（0xC0000005 访问违例：OpenVINO NPU 原生层崩溃，进程级、try/except 抓不到）"}
```

然后继续跑其它设备并正常落盘。**任何要碰 NPU 的新脚本都应该照这个模式写。**

**对结论的影响**：见 [docs/02 第七节](02-实验结论汇总.md#七2026-10-15-重跑对照outputresultsrerun)。
一句话：JEV 的 NPU 招牌数字（189 ms）在当前机器上**无法复现**，
它作为历史测量仍可读，但别承诺"现在跑一遍能得到"。
