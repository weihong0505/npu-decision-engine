## 0. 一句话

**把 JEV-lite（150M 类型化决策引擎）和 Qwen2.5 拉到 Intel NPU 上量了一遍，答案是：NPU 只配跑「静态形状的编码器前向」（比 CPU 快 1.5–1.8×），不配跑自回归解码（慢 3.9–5.5×）。**

（`1.5–1.8×` = 长度扫描 L=128→768 的 NPU/CPU = 0.55–0.66，L=128 时 60.7/38.4 = 1.58×、L=256 时 115.3/63.3 = 1.82×；`3.9–5.5×` = 重跑到原测的 NPU/CPU 解码延迟比。这两条 2026-09 原始值 + 2026-10 重跑都对得上，其余数字见 §2。）

三条结论线的一句话版：

| # | 问题 | 答案 | 可信度 |
|---|---|---|---|
| 1 | LLM 解码放 NPU 值不值？ | **不值**。3.6–5.6 tok/s vs CPU 19.7–28.1 tok/s | ✅ 两次独立测量定性一致，倍数会漂 |
| 2 | 编码器前向在 NPU 上快多少？ | **快 1.5–1.8×，前提是静态形状**。动态形状直接编译失败 | ✅ 2026-10 重跑比值曲线重合 |
| 3 | JEV-lite 整图能搬上 NPU 吗？ | **不能整图，只能拆图**（NPU 编码器 + CPU head）。招牌数字 189 ms **现在跑不出来**（段错误） | ⚠️ 历史测量，2026-10 环境回归后不可复现 |

## 2. 三条结论线（原始值 vs 2026-10 重跑）

### 线 1 · LLM 自回归解码：NPU 不如 CPU

| 场景 | NPU | CPU | 原始比值 |
|---|---|---|---|
| 短问答 p50（max_new=24） | 3304.8 ms / 3.6 tok/s | **553.2 ms / 19.7 tok/s** | 5.47× |
| 128 new token | 6.55 tok/s | **28.14 tok/s** | 4.30× |
| 长 prompt / 512 new | 10.6 tok/s | **28.71 tok/s** | **2.71×** |

重跑后 NPU 变快（3.6→5.6、6.55→7.73、10.6→10.64 tok/s），**短场景比值收到 3.88×，长场景 2.71×→2.76× 几乎没动**。

> 结论：**「NPU 慢」定性成立，「慢几倍」不是常数**，随驱动/协议变化。要引用倍数只用 `results-1.5b-long.json` 那份（token 数足，无提前 EOS 偏差）。

### 线 2 · 编码器前向：静态形状是前提

| 形状 | NPU | CPU | iGPU | NPU/CPU |
|---|---|---|---|---|
| **动态 `[?,?]`** | **编译失败** | 37.2 ms | 34.1 ms | — |
| 静态 L=128（INT4） | **38.4 ms**（重跑 40.6） | 60.7 ms（重跑 61.8） | 47.3 ms（重跑 54.7） | 0.63 |
| 静态 L=768（INT4） | **252.8 ms** | 394.4 ms | 382.6 ms | 0.64 |

长度扫描 L=128→768：NPU/CPU = **0.66 / 0.55 / 0.59 / 0.58 / 0.64**，**全程领先、比值稳定**。

> **静态形状不是优化项，是准入条件。** 代价：序列长度写死，换长度要重编译（NPU 2–37 s）。"NPU 更快"只在**编译一次、推理多次**时成立。

### 线 3 · JEV-lite：整图不行，拆图才行

```
整图 → NPU       编译失败（22 个 IsNaN）                 → 只能 CPU 568 ms
补掉 IsNaN → NPU 能编译，但 1625 ms + max_abs_err 0.812  → 精度崩，路是死的
拆图     → NPU   编码器 189 ms + CPU head 0.2 ms = 189 ms → ✅ 曾成立（3.0× 加速）
```

| 轮次 | NPU 编码器（静态 L=768） | 对照：CPU 整图 | 对照：CPU 编码器 | 加速比 |
|---|---|---|---|---|
| 2026-09-22 | 189.0 ms + head 0.2 ms = **189.2 ms** | 568.4 ms | 420.4 ms | **1.35×**（对整图）/ **2.2×**（对同形编码器） |
| 2026-10-15 | **跑不出来（段错误）** | 570.9 ms | 581.2 ms | — |

拆图依据：head 只是 `Linear(768,1)` 在 `gather(label_pos)` 上读值，总共 `1×768 + 1` 两个张量，CPU 上 0.2 ms；把 224 MB 的编码器单独交给 NPU 才有意义。

> ⚠️ **189 ms 是 2026-09-22 的历史测量**。2026-10-15 重跑时，NPU 编译这两张 fp32 图会**直接段错误**（见 §6）。
>
> ⚠️ **「3.0×」这个数字有歧义，引用前先定分母**：README 写的 3.0× 是拿**整图 CPU 568 ms**（`jev-npu-final.json`）除以 189 ms 得到的 3.0×；
> 而拆图方案的**同形对照**是 CPU 编码器 420.4 ms，算出来是 **2.2×**。两个都「对」，但答的不是同一个问题 ——
> 拿 568 当分母会把「head 也被跳过」算进加速里。**对外只引用 2.2× 这个同形比值，或直接说「189 ms 是历史值、现在跑不出来」。**
> 当前环境下唯一站得住的加速结论是结论线 2 的「编码器静态形状快 1.5–1.8×」。

## 3. 模型本身：JEV-lite 是什么（决定这项目有没有意义）

| 项 | 内容 |
|---|---|
| 骨干 | `answerdotai/ModernBERT-base`，**150M**，一次前向 |
| 接口 | 输入「state + 类型化问题」，输出「每个标签 + 校准置信度」，**不写散文** |
| 三种原语 | `noul`（布尔）/ `choice`（枚举）/ `score`（有序刻线） |
| 关键设计 | 候选标签写进输入序列（`<<l>>` 标记），head = `Linear(768,1)` 读标记位，softmax 按题内标签集做 → **schema 是推理时的数据，不是权重里的常量**，换问题不重训 |
| 为什么在 NPU 上必须拆 | head 要按位置 gather，而 gather 位点由运行时输入决定 ⇒ 图里带动态维 ⇒ NPU 不收 |

**本项目自己的模型**（`output/results/ens.txt`，官方 test split，**400 cases / 2000 decisions**；混合权重与温度只在 val 上选）：

| 配置 | accuracy | ECE ↓ |
|---|---|---|
| 微调模型单独（`model only`） | 0.6470 | 0.0739 |
| 冻结探针单独（`probe only`） | 0.6695 | 0.0384 |
| 集成 w=0.50（未锐化） | 0.7005 | 0.1262 |
| **集成 w=0.50 + 锐化 T=0.50** | **0.7005** | **0.0288** |
| TypeSafe Jev 1.13.0（引用值） | **0.7270** | 0.1440 |
| 多数类基线 | 0.4830 | — |

三个读数要注意：

1. **准确率落后商业 Jev 0.0265，但校准好 5 倍**（ECE 0.0288 vs 0.1440）。对「按置信度自动路由、把不确定的丢给人」这种用法，**校准比那 0.03 更重要**。
2. **锐化是免费的**：w=0.50 的集成本来 ECE 0.1262（比单模型还差），加一步 T=0.50 锐化后降到 **0.0288**，accuracy 一点没动。
3. **`eval.txt` 的 0.6490 / 0.0769 不是同一个数**：那是 `04_eval.py` 在「未锐化、按共识分布」口径下的模型单独成绩（1298/2000），与 `ens.txt` 的 `model only` 0.6470 源于不同评估脚本 —— **两处数字并存不是矛盾，是口径不同**，引用时注明出处。

**置信度能路由**（`ens.txt`，test split）：

| 置信阈值 | 覆盖流量 | 该带内准确率 |
|---|---|---|
| 0.90 | 18.5% | **95.41%** |
| 0.80 | 36.6% | 89.06% |
| 0.70 | 53.4% | 82.94% |
| 0.50 | 89.5% | 73.34% |

> `engine/README.md` 上游自报 0.6240 / 0.6705 / 0.6965（w=0.60, T=0.35）。**不是矛盾**：上游用了不同的混合权重，且本项目 `jevlite.pt` 是 09-22 12:38 重新落盘的那份（见 §6），与上游发布的那份不是同一个训练产物。

## 5. 硬约束与坑（前三条是所有 NPU 结论的总开关）

1. **NPU 只接受静态形状**。动态维 → 编译直接失败（`ze_graph_ext_wrap`）。据 Intel 材料，动态形状是 Lunar Lake 一代才有的能力。
2. **NPU 不支持 `IsNaN`**。图里 22 个（总算子 1960），来自 masked-softmax 惯用写法。补掉能编译，但 1625 ms + 精度崩，不如不做。
3. **拆图是唯一可行的路**：编码器给 NPU，head 留 CPU（0.2 ms）。
4. **INT8/INT4 量化在 NPU 上是负优化**：自导 INT8 要 3374 ms（fp32 是 1613 ms）。**别为了省显存去量化**。
5. **dGPU 经 OpenVINO 极慢**：NPU 37 ms 的任务，RTX 5060 要 1481 ms（慢 97%）。**别把 dGPU 当备选**。
6. **ONNX 侧车不能单独改名**：`.onnx.data` 的文件名被写进 `.onnx` 内部的 `external_data.location`，改名要同时改内部引用。
7. **`max_abs_err` 不能当精度指标**：同权重换一条导出路径，隐藏状态就能差 **22.97**（两个 ONNX 权重指纹完全相同），而设备间差异记录里是 **0.024**。**两者不在同一尺度，"NPU 精度够用"这个说法不成立。**
8. **数值一致性没有判据**：目前没有「怎么算一致」的定义 —— 这是 §7 待办第 5 条。

## 6. 三个必须知道的历史包袱

| 包袱 | 事实 | 影响 |
|---|---|---|
| **189 ms 不可复现** | 2026-10-15 重跑，NPU 编译 `jevlite.onnx` / `jev_encoder.onnx` **进程级段错误**（`0xC0000005` / 退出码 `-1073741819`），try/except 抓不到。**同一时刻 INT4 的 `model_q4.onnx` 在 NPU 上正常（252.82 ms）** ⇒ 是这个 fp32 图的编译回归，不是 NPU 坏了 | 招牌数字降级为「历史测量」；根因未隔离 |
| **ONNX 与检查点不同源** | 指纹核对 46/46、47/47 张量全部不一致；输出侧 logits 差 1.65、隐藏状态差 28.5。02:46 导出时 parity 是 6.32e-06（当时同源），`jevlite.pt` 12:38 被 `03_calibrate.py` 重新落盘 | **延迟结论不受影响**；但「NPU 数字跑在哪份权重上」说不清，模型精度数字与 NPU 数字各属一份权重 |
| **TURBO 是伪影** | 单次扫描称 TURBO 快 **+14.7%**；配对 A/B（4 轮交替）测得 **−0.72%**，轮间波动 2.15%；重跑配对又得 **+1.02%**，波动 7.01% | 采信配对结果：**TURBO 无可靠收益**。`modernbert-tuned.json` 保留但标注「非配对测量，不作结论依据」 |

> 这三条的处理原则值得记：**失效的行不删，原样留在表里并标注**。只展示成功数据的基准不可信。

**顺手记两处文档失准**（不影响结论，但引用前要知道）：

- `docs/04-复现手册.md` 与 `output/onnx/README.md` 写「ONNX 约 7 GB」，**2026-11-13 实测 `output/onnx/` 是 3.57 GB**（2026-10-15 删掉 6 个被取代文件后没同步这两个数字）。

## 8. 为什么这个项目值得公开

一句话：**它给的是一个带具体数字的「NPU 能干什么、不能干什么」判据，而不是又一篇 TOPS 规格表复述。**

对外部读者，这个仓库真正稀有的三点：

1. **负结果是主结论**。市面上讲 NPU 的文章几乎都在讲「快」，这里直接量出「自回归解码慢 3.9–5.5×」「INT8 量化在 NPU 上是负优化（3374 ms vs fp32 1613 ms）」「dGPU 经 OpenVINO 慢 97%」——这三种坑没人写，但每个打算上 NPU 的人都会撞上。
2. **失效的数字不删**。189 ms 那一行跑不出来了，就原样留在表里标注「历史测量」，并把段错误（`0xC0000005`）的定位过程、已排除假设、工程对策（子进程隔离）全部写出来。**「只展示成功数据的基准不可信」这句话，这个仓库是用自己的失败当证据兑现的。**
3. **每个数字都有生产者脚本 + 溯源字段**。19 个原始结果全部保留，重跑结果另存 `rerun/` 并自带 `generated_by` / `generated_at` / `openvino` / `host`，**19 个结果文件里 16 个能一键重跑**（剩下 3 个明确标注「不可复现 + 原因」）。

对熟悉这块的读者，最值得看的是 **`docs/02` 的冲突裁决**和 **`docs/03` 的踩坑排序**：TURBO 单次扫描 +14.7% 被配对 A/B 测成噪声、同权重两条导出路径隐藏状态差 22.97 却常被当成「NPU 精度 0.024」——这两条是方法论层面的东西，比任何一个延迟数字都值钱。

> 局限也要说在前面：本项目**不训练新模型**、**不追求 SOTA**、**不与商业 Jev 做同条件比较**（它的 0.727 是零样本成绩，而本项目的模型在 1,016 条同分布样本上训练过——这个比较框架对 Jev 更不利）。边界见 `docs/01-背景与目标.md`。
